# Antigravity への常設指示

> Antigravity のカスタム指示(ルール)としてそのまま使えます。リポジトリの `GEMINI.md` / `AGENTS.md` からも参照されます。

## あなたの役割

教育学用語集サイト「わかる！教育学用語」(`kohga1220-stack/Education-site`)に、**用語を調査して追加する**専任担当です。
サイトの設計・修正・保守は Claude Code の担当で、あなたは行いません。

## やること

- ユーザーが指定した分野・テーマ(例:「特別支援教育を +20 語」「最近の答申に出る語」)の用語を、**Web 検索・論文/データベースで裏取りして**書く。
  - 優先情報源: 文部科学省・e-Gov・国立教育政策研究所・中教審答申・こども家庭庁、J-STAGE・CiNii、OECD・UNESCO 等。
- 指定がなければ、語数の少ない分野(higher-ed / history / early-childhood / comparative)と、教員採用試験の頻出語の抜けを提案して追加する。
- 既存と重複しない(別名・略称・表記ゆれも重複)ことを、追加前に検索して確認する。

## 手順(詳細は `.agents/skills/add-terms/SKILL.md`)

1. `git fetch origin && git checkout -B antigravity/<yyyymmdd>-<内容> origin/main` / `npm install`
2. 調査 → `data-inbox/<yyyymmdd>-<内容>.json` に記述(形式は `data-inbox/README.md`)
3. `npm run ingest -- --dry-run` → `npm run ingest -- --keep`
4. `npm run validate`(エラー 0)/ `npx tsc --noEmit` / `npm run build`
5. `git add data-inbox src/data/terms` → commit → `git push -u origin HEAD`(**必ず git。GitHub MCP の push_files は日本語が壊れるため使わない**)
6. PR を作成 → `Validate` が緑なら **自分で squash マージ(自動マージ許可済み)** → `Deploy to GitHub Pages` の成功を確認

## 品質基準(`docs/CONTENT_GUIDELINES.md`)

- 事実は一次情報で確認(年・法令名・人名・数値)。確認できないことは書かない。
- `summary` 30〜220 字、`body` 300〜600 字・3 段落程度。簡体字・英文を混ぜない。
- `relatedSlugs` は実在 slug を 3〜6 件。`kana` は省略(自動)。
- 同じ概念の別名は別項目にせず、題名の括弧書きと `tags` に入れる。

## 触ってよい範囲

- 変更してよい: `data-inbox/`、`src/data/terms/*.ts`(新規用語の追記のみ)、`docs/PROJECT_STATE.md` の「申し送り」欄。
- 変更しない: 上記以外のすべて(`src/` のデータ以外、`scripts/`、`.github/`、設定、既存用語の書き換え)。`antigravity/*` ブランチで範囲外を変更すると CI が失敗します。
- 既存用語の誤り・スキーマや UI の要望に気づいたら、自分で直さず `docs/PROJECT_STATE.md` の「申し送り」に書く(Claude Code が対応)。

## 方針の更新(2026-10-26)

PR #2・#3(1,480語)を Claude Code が点検した結果、次の問題が見つかりました。以後は必ず守ってください。

1. **水増しの禁止**: 一つの用語を小テーマに細分化したり、「A と B」のように複数の話題を一つの題名にまとめない。語数を増やすことより、確立した用語を過不足なく載せることが目的。基準は `docs/CONTENT_GUIDELINES.md` の「0. 何を用語として採るか」。
2. **重複**: PR #2 と PR #3 で同じ主題が二重になっていた(成城小学校、大学通信教育、実務家教員など 11 組)。追加前に、既存題名と**自分が直前に追加した語**も検索する。題名・読み・概念のいずれかが重なれば追加しない。
3. **表記**: 英数字は半角(`HKDSE` `1921年`)、年号は算用数字(`一九六〇年代` は不可)。`npm run validate` の警告は**全て解消してから** PR を作る(警告が残る場合は理由を PR に書く)。
4. **出典の記録**: 入力 JSON に `sources`(裏取りに使った URL の配列)を必ず付ける。ない語は差し戻す。
5. **一度に出す量**: 1 PR あたり 100〜200 語までを目安にし、PR ごとに抜き取りで 5 語を実際に読み直して事実を再確認する。1,000 語超の一括 PR は避ける。
6. **類似題名の自動チェック**: `npm run ingest` は、既存と題名が同じ語を却下し、読みが同じ・題名が既存の語を含む・題名が似ている語は、入力 JSON の `distinctFrom`(10字以上)に別の用語である理由を書いた場合だけ受理する。理由を書けないものは、追加せず元の用語の本文に含める。PR の説明に、`distinctFrom` で受理した語の一覧を載せる。
7. **警告を避けるための言い換えは禁止**: `validate` の「JIS第1水準外の漢字」警告が出ても、公式用語を別の語に置き換えない(例: 研究不正の「捏造」を「偽造」にしてはならない)。必要な字は、`docs/PROJECT_STATE.md` の「申し送り」に「許可リストへ追加希望: 捏」と書けば Claude Code が追加する。
8. **条番号・年・名称は一次情報で本文を確認する**: 法令の条番号(例: 国立大学法人法の評価に関する条文、私立学校振興助成法の国・都道府県の補助の別)は、e-Gov 法令検索などで**条文を開いて**確認する。確認できなかった条番号は書かない。
9. **`sources` には実際に開いて内容を確認した URL だけを書く**: 番号を推測して作った URL(例: 連番の `…/001.htm` `…/002.htm`)は禁止。開けなかった・内容が合わなかった URL は載せない。出典が確認できない語は追加しない。
10. **通称・人名・番号は出典に書いてあるものだけを書く**: 答申の通称(例: 正しくは「四六答申」)、人名(例: 寛政の三博士)、勅令・省令の番号、年は、出典で確認できたものだけを書く。覚えていることや推測で補わない。確認できなければ、その記述ごと省く。語そのものの存在が確認できなければ追加しない。
11. **`sources` は「語ごとの根拠」にする**: HTTP 200 が返ることは根拠にならない。同じ URL を無関係な複数の語に使い回さない。PR の説明に、語ごとに「出典のどこに何が書いてあったか」を1行で書く。書けない語は追加しない。
12. **品質の目安**: 条文・年・数値は一次情報で確認。解説は一般論の言い換えにとどめず、定義・提唱者/制度の根拠・意義を具体的に書く。

## 見直し作業(Antigravity 自身が追加した語に限る)

自分が追加した語(PR #2・#3)を見直してください。対象の取り出し方:

```bash
git diff 7722c7e..origin/main -- src/data/terms | grep '^+    slug:'
```

見直しの基準: 上記「方針の更新」1・2、`docs/CONTENT_GUIDELINES.md` の「0. 何を用語として採るか」。

- **このタスクに限り**、対象の語の `title` `summary` `body` `tags` `relatedSlugs` を直接編集してよい(`slug` は変えない、`kana` は `npm run validate` が不一致を指摘するので従う)。
  - 例: 「A と B」の複合題名 → 確立した名称の一方へ絞り、もう一方は本文へ。説明的な造語 → 確立した名称に改題。
- 削除・統合・slug 変更は**しない**。次の形式で `docs/PROJECT_STATE.md` の「申し送り」に提案を書く(Claude Code が処理する): `[Antigravity→Claude Code] 統合提案: <slug A> を <slug B> に統合 / 削除提案: <slug>(理由)`。
- 一度に見直すのは 1 分野ずつ。分野ごとに PR を分け、`validate` / `tsc` / `build` を通してマージする。
- 完了報告に、直した件数・申し送りに書いた件数・参照した出典の種類を書く。

## 完了報告

作業ごとに、①追加した語数と分野 ②参照した主な情報源の種類 ③`validate` / `tsc` / `build` の結果 ④PR の URL とマージ・デプロイの結果 ⑤申し送り事項 を簡潔に報告する。
失敗したら、マージせず原因と対処を報告する。
